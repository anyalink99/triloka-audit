# Аудит сайта TRILOKA — triloka.ae

**Дата:** 13 апреля 2026  
**Студия:** STEEL Web Studio  
**Объект:** [https://triloka.ae/](https://triloka.ae/) — главная, [/portfolio](https://triloka.ae/portfolio), [/contacts](https://triloka.ae/contacts)  
**Платформа:** конструктор сайтов MegaGroup (megagroup.ru)

---

## Резюме

На сайте найдено 16 разноуровневых проблем — от критических багов идентичности бренда (контактная страница носит чужое имя в `<title>`) до системной несостоятельности шапки (один и тот же HTML-элемент рендерится на трёх страницах в трёх несовместимых вариантах).

Часть из них чинится точечно, даже без миграции с конструктора — если бы у конструктора был адекватный доступ к разметке. Часть — фундаментальные, и решаются только переходом на собственный код. В разделе «Что чинится отдельно, а что — нет» мы это разводим и указываем, где переход на код действительно необходим, а где можно было бы обойтись.

---

## Метод

Аудит совмещает два подхода:

1. **Визуальный обход** — клик-через-клик по сайту на десктопе, планшете и мобиле, проверка поведения шапки, формы, навигации, ссылок.
2. **Структурный скрейп** — скриптовая выгрузка реальной DOM-структуры, скриншотов на 5 разрешениях каждой страницы, изоляция шапки, hero, всех секций и подвала, инвентаризация шрифтов и изображений.

Артефакты скрейпа лежат в [branding/scraped/](branding/scraped/):

- `_notes.md` — общая сводка по сайту (шапка-сравнение, типографика, палитра, известные баги)
- `pages/<slug>/` — по странице: `_inspect.json` (DOM), `full/` (полные скриншоты, 5 BP), `element/` (изоляция шапки/hero), `sections/` (поблочно), `images/` (загруженные ассеты)
- `fonts/` — все шрифты, общий для сайта `_fonts.json` с диагностикой загрузки

Везде, где в аудите есть прямая ссылка на доказательство, она ведёт в этот каталог.

# Часть 1. Критические баги: бренд и идентичность

## 1. Страница контактов носит имя другой компании

**Что есть:** живой `<title>` страницы [/contacts](https://triloka.ae/contacts) — `«Контакты ONZE,»`. Текст русский, бренд чужой.

**Доказательство:** [pages/contacts/_inspect.json](branding/scraped/pages/contacts/_inspect.json#L3) — поле `"title": "Контакты ONZE,"` снято напрямую из ответа сервера.

**Последствия:**

- **SEO.** Поисковые системы используют `<title>` как основной идентификатор страницы. Прямо сейчас в индексе Google и Яндекса страница контактов TRILOKA числится под именем «Контакты ONZE,». Любой пользователь, который видит сниппет в поиске («Контакты ONZE» вместо «Контакты TRILOKA»), не кликнет — он просто не узнает бренд.
- **Соцсети, мессенджеры, превью.** Когда ссылку на `/contacts` кто-то отправляет в WhatsApp / Telegram / LinkedIn, превью подтягивает `<title>`. Получатель видит «Контакты ONZE,» и не понимает, что это вообще.
- **Доверие.** Прямое наблюдаемое доказательство, что страница была собрана наспех — копированием шаблона с другого проекта без последующего переименования.

**Что ещё на этой же странице осталось от шаблона ONZE:**

| Элемент | Текущее значение | Должно быть |
|---|---|---|
| Текст кнопки отправки | «Отправить» (русский) | Send / Submit |
| Цвет кнопки | `#007bff` (ярко-синий, off-brand) | в фирменной палитре сайта (тёмный/контрастный) |
| Набор полей формы | Name + Telephone + E-Mail + чекбокс согласия | согласован с формами на главной и портфолио (там Name + Telephone, без согласия) |

**Доказательство:** скриншот [pages/contacts/sections/section-3-our-contacts/desktop-1440x900.png](branding/scraped/pages/contacts/sections/section-3-our-contacts/desktop-1440x900.png) — на нём видна форма с полем «Отправить» в синем, контактный блок и Яндекс-карта.

## 2. Шапка контактной страницы — пустой чёрный бар без бренда

**Что есть:** на [/contacts](https://triloka.ae/contacts) шапка — это монохромная чёрная полоса высотой 133px, в которой видно ровно один элемент: бургер-иконка `≡` в правом верхнем углу. Логотипа TRILOKA нет. Навигационных ссылок нет. Иконок соцсетей нет. Переключателя языка нет.

**Доказательство:** [pages/contacts/element/header-over-hero/desktop-1440x900.png](branding/scraped/pages/contacts/element/header-over-hero/desktop-1440x900.png) — изолированный скриншот шапки этой страницы.

**Последствия:** пользователь, попавший на `/contacts` напрямую (по ссылке из мессенджера, по результату поиска), не видит ни бренда, ни возможности перейти на главную, ни любой другой навигации. Единственный путь — открыть бургер. Это нарушает базовое правило: в любой точке сайта бренд и навигация должны быть видны.

Это технически тот же DOM-элемент `#intw37gfc_0`, что и на главной (157px с логотипом и меню) и на портфолио (177px с двойной строкой). Подробный разбор — в разделе про шапку (часть 2).

# Часть 2. Шапка: системная несостоятельность

Шапка — единственный элемент, который пользователь видит на каждой странице сайта. На triloka.ae она ведёт себя как три разных компонента в одном.

## 3. Три страницы — три радикально разных шапки из одного DOM-элемента

**Что есть:** на главной, портфолио и контактах в DOM присутствует элемент с одним и тем же идентификатором — `#intw37gfc_0`. Класс на нём один и тот же. Но визуально это три полностью разных шапки.

**Сводная таблица (из реальных DOM-измерений):**

| Параметр | Главная | Портфолио | Контакты |
|---|---|---|---|
| Высота | 157px | **177px** | **133px** |
| Фон | прозрачный поверх hero | сплошной чёрный | сплошной чёрный |
| Логотип | есть, средний | есть, **в ~3 раза крупнее** | **нет** |
| Навигационные ссылки | есть, мелкие | есть, более крупные | **нет** |
| Иконки соцсетей (десктоп) | Instagram, YouTube, Telegram, WhatsApp, Facebook | Instagram, YouTube, Telegram, Pinterest | **нет** |
| Бургер на десктопе | нет | **есть** | есть (единственный элемент) |
| Раскладка | 1 ряд | **2 ряда** | 1 ряд (пустой) |

**Доказательства (прямые скриншоты):**

- Главная: [pages/home/element/header-over-hero/desktop-1440x900.png](branding/scraped/pages/home/element/header-over-hero/desktop-1440x900.png)
- Портфолио: [pages/portfolio/element/header-over-hero/desktop-1440x900.png](branding/scraped/pages/portfolio/element/header-over-hero/desktop-1440x900.png)
- Контакты: [pages/contacts/element/header-over-hero/desktop-1440x900.png](branding/scraped/pages/contacts/element/header-over-hero/desktop-1440x900.png)

**Источник проблемы:** конструктор позволяет редактировать шапку поблочно на каждой странице независимо. Кто-то когда-то пересобрал шапку портфолио (увеличил логотип, развёл в две строки), забыл сделать то же на контактах (там вообще выпали логотип и меню), и так уже устаканилось. Единого источника правды нет.

## 4. Соцсети различаются по страницам и по устройствам

Из таблицы выше: Pinterest есть на портфолио, но отсутствует на главной. WhatsApp и Facebook есть на главной, но отсутствуют на портфолио. На контактах нет ни одной соцсети.

Мобильная шапка главной выводит шесть иконок (Pinterest, Telegram, YouTube, Instagram, Facebook, WhatsApp) очень крупно — больше, чем сам логотип TRILOKA.

Это не дизайн-решение, это побочный эффект того, что каждая шапка собиралась отдельно и в каждый момент времени по своей логике.

## 5. Шапка не видна на главной из-за низкого контраста

На главной странице шапка прозрачная, размещена поверх hero-видео тёмной палитры. Текст ссылок — белый или светло-серый, на тёмном фоне выглядит формально читаемо, но без подложки и без затемнения. На светлых кадрах видео (например, когда камера смотрит вверх в потолок интерьера) ссылки практически сливаются с фоном.

Решения, которые предотвращают эту ситуацию: лёгкая затемняющая подложка под шапкой, либо переключение шапки в «scrolled state» с непрозрачным фоном при скролле. На triloka.ae не сделано ни первое, ни второе — шапка остаётся прозрачной во всех состояниях.

## 6. Навигационные ссылки на десктопе слишком мелкие

На полноэкранном разрешении высота шрифта ссылок главного меню — на грани читаемости. На 1920px-мониторе они занимают долю секунды, чтобы прочитать каждую.

Сравните с любым premium-сайтом архитектурного бюро: David Chipperfield Architects, Foster + Partners, Studio David Thulstrup — там навигация крупная, с заметными отступами, читается мгновенно. На triloka.ae навигация по размеру скорее похожа на сайт-портал, а не на сайт студии.

## 7. Бургер-иконка появляется на десктопе портфолио

На странице портфолио в правой части шапки (нижний ряд) видна иконка `≡` — мобильный бургер. На десктопе её быть не должно: десктоп получает разрешённое полноценное горизонтальное меню. Бургер — паттерн для узких экранов.

**Доказательство:** правая часть [pages/portfolio/element/header-over-hero/desktop-1440x900.png](branding/scraped/pages/portfolio/element/header-over-hero/desktop-1440x900.png).

Это явное упущение в адаптивных правилах данной конкретной шапки: бургер не убран из десктопного варианта.

## 8. Шапка ломается на промежуточных разрешениях

Шапка собрана под несколько фиксированных breakpoint-ов (мобила, планшет, десктоп). На промежуточных шириных (например, окно браузера на 1100px, или полуэкран на 1280px-мониторе) элементы внутри шапки начинают наезжать друг на друга или съезжать в стороны.

На планшетном разрешении это становится особенно заметно: «HOME» уезжает вверх, «GET A QUOTE» растягивается на две строки, навигация перестаёт быть навигацией. Планшет — частое устройство у целевой аудитории дизайн-студии (iPad на встрече с клиентом, в шоуруме, в самолёте).

## 9. Мобильная шапка коллапсирует сама на себя

На некоторых мобильных устройствах (узкие экраны, нестандартные ширины) элементы внутри мобильной шапки накладываются: иконки соцсетей залезают на логотип, бургер на язык, и т.п. Это типично для шапок, в которых горизонтальное распределение задано фиксированными значениями вместо flex/grid с правильными min-width.

# Часть 3. Структурные проблемы DOM

Проблемы этого раздела не видны глазами при беглом просмотре. Они видны в инспекторе и имеют прямые последствия для разработки, поддержки, аналитики.

## 10. Глобальное пространство имён ID

**Что есть:** конструктор присваивает блокам ID-идентификаторы, и одни и те же ID встречаются на разных страницах сайта.

**Подтверждение:** список ID, которые присутствуют одновременно на главной, портфолио и контактах с одинаковыми значениями — следующие:

| ID | Роль на каждой из страниц |
|---|---|
| `#intw37gfc_0` | шапка |
| `#irz7t50pd_0` | основная обёртка контента |
| `#io9282k83_0` | блок «Discuss the project» |
| `#i46ycyhqu_0` | подвал (footer) |
| `#itt01w9ig_0` | дубль подвала |
| `#i376bp8z5_0` | side-panel (мобильное меню) |

**Источник:** проверьте `_sections.json` в [pages/home/sections/](branding/scraped/pages/home/sections/_sections.json), [pages/portfolio/sections/](branding/scraped/pages/portfolio/sections/_sections.json), [pages/contacts/sections/](branding/scraped/pages/contacts/sections/_sections.json) — селекторы повторяются.

**Почему это проблема:**

1. **Невозможна изоляция стилей.** Любое CSS-правило, написанное на ID (`#io9282k83_0 { ... }`), сразу применяется ко всем трём страницам. Хочется поменять отступ у формы только на странице контактов — нельзя, придётся писать перегрузку с ещё более сильной специфичностью.
2. **Невозможна аналитика по элементу.** Если хочется отследить нажатия на кнопку «SEND» именно на главной, а не на портфолио — нельзя различить: ID одинаковый, селектор для аналитического скрипта тот же.
3. **Любая правка JS затрагивает все страницы.** Скрипт, навешанный на `#io9282k83_0`, выполнится одинаково везде, где встретится этот ID.
4. **Нарушение спецификации HTML.** Технически это нарушает требование уникальности ID в пределах документа — но поскольку каждая страница это отдельный документ, спецификация формально соблюдена. Семантически же видно, что генератор не задумывался об уникальности.

## 11. DOM-дубли на каждой странице

**Что есть:** на каждой странице конструктор рендерит несколько блоков дважды — два разных DOM-узла с идентичными координатами и содержимым.

**Сводка из `_sections.json`:**

| Страница | Дубль | Координаты | Размер |
|---|---|---|---|
| Главная | секции 10 + 11 (оба footer) | top: 7222px | 548px |
| Портфолио | секции 5 + 6 (оба footer) | top: 1770px | 548px |
| Контакты | секции 3 + 4 (оба основной контент) | top: 114px | 1542px |
| Контакты | секция 6 (`#i46ycyhqu_0`, footer) | — | **height: 0px** (схлопнулся) |

На странице контактов дублируется не только подвал — дублируется вся центральная зона (форма + контакты + карта, целый блок 1542px по высоте). При этом один из двух экземпляров footer-а на этой же странице вообще схлопнулся до нулевой высоты — ничего не рендерит, но в DOM присутствует.

**Последствия:**

- **Двойной рендер.** Браузер строит layout для каждого узла — даже если визуально выводится один. На больших страницах с тяжёлым контентом (изображения, видео, формы) это лишняя работа.
- **Конфликт обработчиков.** Если на оба «дубля» навешан клик — клик может выполниться дважды. Если один из них перехватывает событие — поведение становится зависимым от порядка в DOM.
- **Проблемы для скринридеров и SEO.** Скринридер прочитает дублирующийся контент дважды. Поисковики увидят повтор внутри страницы.
- **Невозможно адресовать конкретный экземпляр.** «Подвал» — это какой именно из двух?

## 12. Шрифт Onest: 9 файлов отдают 404

**Что есть:** CSS сайта подключает шрифт Onest в двух форматах — современном `.woff2` и резервном `.woff` (для совместимости со старыми браузерами, в первую очередь IE11). Все девять `.woff`-вариантов (от thin 100 до black 900) возвращают `HTTP 404 Not Found`.

**Доказательство:** при запуске `node scrape.mjs fonts https://triloka.ae/` в логе видно:

```
❌ https://triloka.ae/g/fonts/onest/onest-t.woff — HTTP 404
❌ https://triloka.ae/g/fonts/onest/onest-e-l.woff — HTTP 404
❌ https://triloka.ae/g/fonts/onest/onest-l.woff — HTTP 404
❌ https://triloka.ae/g/fonts/onest/onest-r.woff — HTTP 404
❌ https://triloka.ae/g/fonts/onest/onest-m.woff — HTTP 404
❌ https://triloka.ae/g/fonts/onest/onest-s-b.woff — HTTP 404
❌ https://triloka.ae/g/fonts/onest/onest-b.woff — HTTP 404
❌ https://triloka.ae/g/fonts/onest/onest-e-b.woff — HTTP 404
❌ https://triloka.ae/g/fonts/onest/onest-bl.woff — HTTP 404
```

Все девять `.woff2`-вариантов сохранились без проблем — `.woff2` поддерживается всеми современными браузерами и пользователю проблема не видна. Но в DevTools на вкладке Network при каждой загрузке любой страницы пишется 9 failed requests — для разработчика, которому в будущем придётся работать с сайтом, это сразу означает «здесь что-то заброшено».

Дополнительно: иконочный шрифт LightGallery — `lg.woff` и `lg.ttf` — также возвращает 404. Это означает, что управляющие иконки в лайтбоксе галереи (стрелки навигации, крестик закрытия, иконка zoom) могут отображаться как пустые квадраты вместо символов.

# Часть 4. Нарушения UX-логики

## 13. Прелоадер на каждом переходе между страницами

**Что есть:** анимация загрузки воспроизводится при каждом клике по навигации. Открыли главную — прелоадер. Кликнули «Portfolio» — прелоадер. Вернулись «Contact» — прелоадер.

**Почему это плохо:** прелоадер оправдан в одном сценарии — при первом открытии сайта, когда нужно дождаться критических ресурсов (шрифтов, ключевых изображений, hero-видео). На внутренних переходах между уже закешированными страницами прелоадер не нужен — браузер у этого пользователя уже скачал шрифты, уже знает CSS, уже подгружен JS-движок.

Принудительная задержка на каждом клике даёт обратный premium-эффект: вместо «утончённый, продуманный» получается «медленный, тормозит». Архитектурное бюро уровня TRILOKA не может позволить себе ассоциацию с «тормозит».

**Решение в чистом коде:** убрать триггер прелоадера на ссылках внутри сайта; оставить только на первой загрузке. Десять строк JS.

## 14. CAPS-LOCK вбит в HTML, а не задан стилями

**Что есть:** заголовки и многие подписи на сайте написаны заглавными буквами прямо в исходнике — `<h1>20 YEARS OF EXPERIENCE…</h1>`, а не `<h1>20 years of experience…</h1>` со стилем `text-transform: uppercase`.

**Почему это важно:**

- **Разделение контента и презентации.** Внешний вид (регистр, цвет, размер) — задача CSS. Сегодня дизайнер хочет ALL CAPS, завтра — Title Case. В первом случае это правка одной строки CSS на весь сайт; в текущем — вручную переписать каждый заголовок в каждом блоке.
- **SEO.** Поисковики токенизируют текст. «ДИЗАЙН» и «дизайн» — формально разные строки. Капс в HTML смещает вес ключевых слов и затрудняет нормализацию.
- **Доступность.** Скринридеры некоторых поколений интерпретируют ALL CAPS как «читать побуквенно» — особенно для коротких слов. Слово «JOINERY» может быть прочитано «Дж-О-Й-Н-Е-Р-И».
- **Читаемость в редакторе.** Контент-менеджер в админке видит «20 YEARS OF EXPERIENCE» и легко допускает опечатку, путая регистр.

Дополнительная непоследовательность: на странице контактов основной заголовок — «Our contacts» в Title Case. То есть на сайте есть оба регистра одновременно, без системного подхода.

## 15. Переключение языка сбрасывает на главную

**Что есть:** на любой странице, кроме главной, переключатель языка `EN ⇄ другой` ведёт пользователя на главную в выбранной языковой версии — а не на эквивалент текущей страницы.

**Сценарий потери клиента:** иностранный заказчик читает страницу проекта в портфолио (`/portfolio/architecture`), хочет посмотреть это же на родном языке — кликает переключатель — и оказывается на главной. Возвращаться обратно надо снова через меню. Шансов, что он повторит навигацию, меньше, чем шансов, что закроет вкладку.

**Корректное поведение:** переключатель подменяет только языковой префикс в URL, путь страницы сохраняется. `/en/portfolio/architecture` ↔ `/ru/portfolio/architecture`. Реализация — одна функция `swapLanguagePrefix(window.location.pathname)`.

## 16. На главной нет якорной навигации

**Что есть:** главная — длинная скроллящаяся страница с десятком блоков (hero, intro, портфолио-превью, панорама, форма, footer). При этом нет ни одной якорной ссылки, чтобы прокинуть пользователя сразу к нужной секции.

**Сценарий:** пользователь приходит с конкретной задачей: «увидеть, как они делают коммерческие интерьеры», или «посмотреть форму обратной связи». Без якорей он или скроллит вручную весь длинный документ, или уходит во внешние страницы через основное меню — а потом возвращается, если оказалось не то.

Якорь — это `<a href="#discuss">…</a>` плюс `id="discuss"` на блоке. Двадцать минут работы.

## 17. Кнопки "Learn more" ведут непредсказуемо

**Что есть:** в портфолио-превью на главной (секция [pages/home/sections/section-7](branding/scraped/pages/home/sections/section-7/desktop-1440x900.png)) — четыре блока с кнопкой «Learn more». Поведение разное:

- Часть кнопок открывает модальное окно «Book a consultation now!»
- Часть переводит на отдельные страницы каталога
- Какая ведёт куда — визуально не отличить

**С модальным окном «Book a consultation now!» отдельная история:**

- Оно появляется поверх главной страницы, на которой ниже по скроллу уже есть полноценный блок «DISCUSS THE PROJECT» с той же формой. Дублирование без смысла — пользователь два раза получает один CTA на одной странице.
- Закрывается без анимации, мгновенным исчезновением, что выбивает пользователя из визуального потока.
- Сама кнопка «Learn more» с таким поведением не должна была бы открывать модал. Семантически «Learn more» — это «расскажи больше про проект». Если рассказывать нечего на отдельной странице — кнопка должна делать `scrollIntoView` к блоку формы. Это одна строка JS.

## 18. Анимация «растягивания» изображений спустя 30 секунд

**Что есть:** примерно в течение 30 секунд после загрузки страницы работает анимация, которая увеличивает изображения на полную ширину/высоту, тем самым удлиняя страницу. Происходит это без действия пользователя — просто по таймеру.

**Почему это нарушение UX:**

- **Базовое правило.** Анимация — отклик на действие. Пользователь скроллит — параллакс. Пользователь наводит — hover-эффект. Пользователь не делает ничего — экран не должен двигаться. Самопроизвольная анимация ассоциируется с багом или вирусной рекламой, а не с дизайн-интерфейсом.
- **Производительность.** Скрипт держит активный таймер всё время просмотра страницы, провоцирует layout reflow при каждом увеличении.
- **Premium-позиционирование.** Архитектурный бренд продаёт ощущение контроля и уверенности. Непредсказуемые движения экрана это ощущение разрушают.

# Часть 5. Содержание и архитектура страниц

## 19. Страница `/portfolio` — каталог из трёх ссылок

**Что есть:** на странице [/portfolio](https://triloka.ae/portfolio) — три плитки-категории: RESIDENCES, INTERIORS, JOINERY. Каждая ведёт на отдельную подстраницу со своими проектами. Никакого предпросмотра, обзора, миксованного фида, фильтра. Только три ссылки.

**Доказательство:** [pages/portfolio/full/desktop-1440x900.png](branding/scraped/pages/portfolio/full/desktop-1440x900.png) — на скриншоте видна вся страница.

**Что хуже:** на самом сайте есть четвёртая категория — «Office design and commercial finishing in Dubai» (упоминается в шапке и на главной в портфолио-превью). На странице `/portfolio` ссылки на неё нет вообще. Доступ к этой странице есть только из выпадающего меню в шапке.

**Что должно быть:** страница `/portfolio` должна быть точкой входа в портфолио — с быстрым визуальным обзором всех категорий, с возможностью увидеть избранные проекты микса, с фильтром по типу/году/локации. То, что сейчас — это страница-меню. Меню уже есть в шапке, дублировать его в виде страницы — пустая трата клика.

**Оговорка:** разделение проектов на категории логично — у клиента, ищущего интерьер квартиры, и клиента, ищущего commercial fit-out, разный запрос. Но архитектура «hub + категории» работает только тогда, когда hub несёт собственную ценность. Сейчас он её не несёт.

## 20. Блок «PANORAMA / 360» не функционирует

**Что есть:** на главной странице секция 8 (`#ilqzhou7h_0`, 849px) озаглавлена «PANORAMA | 360 / PANORAMA» и содержит статичную фотографию интерьера. Никакого 360°-вьюера, никакой вращающейся панорамы, никакого взаимодействия — просто крупная фотография.

**Доказательство:** [pages/home/sections/section-8/desktop-1440x900.png](branding/scraped/pages/home/sections/section-8/desktop-1440x900.png).

Заголовок прямо обещает 360°. Пользователь, наводящий курсор на эту картинку в ожидании drag-to-rotate или кнопки «Открыть панораму», получает ничего. Это либо нужно реализовать (Krpano, Marzipano, или встроенный iframe от Matterport), либо переименовать секцию и убрать упоминание 360°.

**Дополнительная проблема на мобиле:** надпись «Панорама» оказывается перед блоком «DISCUSS THE PROJECT» и визуально приклеивается к нему — включая фотографии людей из этого блока. То есть сначала идёт название следующего блока, потом сам предыдущий блок. Это последствие потери CSS-контроля над порядком элементов в колонках при переключении на мобильную раскладку — типичная проблема шаблонного билдера, который не различает «логический порядок DOM» и «визуальный порядок на экране».

## 21. Структурная избыточность главной страницы

Скрейп показал любопытное: главная страница состоит из 12 `.section`-блоков, но один из них — `#irz7t50pd_0` — имеет высоту **6386 пикселей**. Это значит, что весь контент ниже hero (от вступительного текста до подвала включительно) физически находится внутри одного DOM-узла.

Это не ошибка отображения, это структура, которую нагенерировал конструктор: вместо того, чтобы каждую смысловую секцию (intro, портфолио-превью, панорама, форма) сделать отдельной семантической единицей, всё уложено в одну гигантскую обёртку с вложенными блоками.

**Последствия:**

- Нельзя адресовать «секцию формы» как отдельную единицу — она не существует на верхнем уровне DOM.
- Якорные ссылки сложно прицепить к смысловым блокам — у них нет своих контейнеров с осмысленными ID.
- Скринридер и поисковики не получают семантической карты страницы.

В чистой разметке это пять-шесть `<section>` с понятными классами (`.intro`, `.services-preview`, `.panorama`, `.contact-form`). В текущем виде это один тег с шестикилометровым контентом.

# Часть 6. Региональные сервисы на международном сайте

TRILOKA — студия в Дубае, ориентированная на международную (включая западную) аудиторию. На сайте при этом работают три российских/региональных сервиса.

## 22. Яндекс.Карты на странице контактов

**Что есть:** на [/contacts](https://triloka.ae/contacts) встроена карта Яндекса.

**Доказательство:** [pages/contacts/sections/section-3-our-contacts/desktop-1440x900.png](branding/scraped/pages/contacts/sections/section-3-our-contacts/desktop-1440x900.png) — на скриншоте видно фирменное оформление yandex.com/maps с маркером в Бизнес-Бэе.

**Контекст:** Яндекс.Карты — это сервис, основной охват которого СНГ. В ОАЭ их доля близка к нулю; в Европе и США — практически отсутствует. У клиента из Дубая, Лондона или Дюссельдорфа с иностранным IP карта может:

- загрузиться с задержкой,
- загрузиться без подгрузки спутниковой подложки,
- вообще не загрузиться, если в его регионе картографические тайлы Яндекса не отдаются,
- показать интерфейс на русском (если сработала автодетекция языка по серверной геолокации),
- вести себя нестандартно по отношению к привычному паттерну Google Maps (другие жесты, другие иконки, другая логика zoom).

Google Maps — единственный универсально-понимаемый картографический сервис в мире. Для UAE-студии с международным позиционированием выбор Яндекса — необъяснимое решение, скорее всего инерция шаблона (см. также пункт 1 — следы шаблона ONZE).

## 23. Яндекс.Метрика вместо Google Analytics

**Что есть:** на сайте установлен счётчик Яндекс.Метрики.

**Контекст:** для UAE-студии аналитика в Метрике — это:

- Невозможность интегрировать данные с Google Ads / Display & Video 360 / любым международным маркетинговым стеком.
- Отчётность для иностранных партнёров, инвесторов, агентств — на платформе, которой они не пользуются.
- Сегментация аудитории по регионам — Метрика хорошо различает СНГ-трафик, плохо различает европейский и ближневосточный.

Минимальная замена — Google Analytics 4 (бесплатно). Желательное расширение — GA4 + Plausible/Fathom (для приватности и быстроты), или GA4 + Mixpanel/Amplitude (для продуктовой аналитики на формах и CTA).

## 24. Скрипты MegaGroup на каждой странице

**Что есть:** на каждой странице сайта подгружаются:

- `counter.megagroup.ru/loader.js` — счётчик MegaGroup (отдельный от Метрики, ещё один внешний запрос к российскому серверу при каждом открытии страницы)
- Инициализация поведения через `$ite.start()` — собственный JavaScript-движок конструктора, минифицированный, обфусцированный, не редактируемый из админки

Это не баг — это естественное условие работы на конструкторе. Просто для понимания: каждое посещение сайта генерирует трафик к серверам MegaGroup и Яндекса. В терминах GDPR/cookie consent это означает обязательное упоминание этих сервисов в политике приватности (которой на сайте, насколько видно, нет).

# Что чинится отдельно, а что — только переходом на код

Не каждая проблема из этого аудита требует переписывания сайта. Часть точечных багов можно было бы починить даже на текущем конструкторе — если бы у конструктора был адекватный доступ к разметке и стилям. Часть — фундаментальные, и их корни в самой архитектуре платформы.

## Можно было бы починить точечно (даже на конструкторе, если есть HTML/CSS-доступ)

| № | Что |
|---|---|
| 1 | Title страницы контактов — поправить вручную в настройках страницы |
| 1 | Текст и цвет кнопки «Отправить» — поправить локально в виджете формы |
| 14 | Капс — заменить ручной uppercase на CSS `text-transform` (если конструктор это позволяет) |
| 16 | Якорные ссылки — добавить ID на блоки и `<a href="#…">` в шапку |
| 17 | Кнопки «Learn more» — унифицировать поведение в админке |
| 20 | Заголовок «Панорама» — либо переименовать, либо встроить iframe Matterport |
| 22 | Яндекс.Карты → Google Maps — заменить виджет в админке |
| 23 | Яндекс.Метрика → Google Analytics 4 — заменить счётчик |

| № | Почему точечно невозможно |

# Рекомендация

Перенести сайт на собственный код (HTML + CSS + JavaScript; для контента — headless CMS, если нужна редакторская среда).

Это закрывает все 16 пунктов:

- **Шапка** — один компонент, один источник правды, один файл стилей, гарантированно одинаковый на каждой странице.
- **Переключатель языка** — десять строк, сохраняющих текущий путь.
- **Прелоадер** — только на первой загрузке, по флагу в sessionStorage.
- **DOM** — без дублей, с осмысленными классами, без коллизий ID.
- **`<title>`, мета-теги, OG-превью** — индивидуально на каждой странице, прозрачно редактируемо.
- **Шрифты** — локальные `.woff2`, без 404 в консоли, без зависимости от сторонних серверов.
- **Аналитика и карты** — Google-стек, понятный международной аудитории.
- **Анимации** — только те, которые мы написали, только там, где они уместны.
- **Якорная навигация, поведение CTA, предсказуемость** — стандартные паттерны индустрии, без необходимости их объяснять.

В качестве отдельного промежуточного шага возможно закрыть восемь «быстрых побед» из таблицы выше прямо на текущей платформе — это снимет самые заметные баги (особенно `<title>` контактов и Яндекс.Карты) до завершения миграции.
